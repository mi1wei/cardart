## 1. 目标

把现有的 3D 翻阅卡册改造成**本地相册管理工具**：

- 照片存在自己的电脑上；
- 在浏览器里建相册、上传、排序；
- 用 3D 翻阅的方式看，一页按照片横竖自动排多张；
- 同一 Wi‑Fi 下，手机扫码也能看、能上传。

以后会打包成安装版，按授权码订阅（子项目 2）。本期为它留好接口，但不实现。

## 2. 共识

用户说的：

- 「我只想做一个本地的相册管理工具，你觉得用什么样的形式展示给用户，目前已经实现了3d翻阅」
- 内容：日常照片，横竖混合，按旅行、家庭等分本（选 B）。
- 存储与设备：照片存在电脑上，同一 Wi‑Fi 下手机也能看（选 B）。
- 管理：在网页里建相册，从电脑或手机上传，排序、设封面、删除（选 B）。
- 「后期需要搞成订阅制」。形式是装在用户电脑上的软件，照片不出本机，「我会提供给他授权码」（选 A）。
- 数据结构参考用户给的目录树：`library.db`，以及 `albums/<uuid>/` 下的 `album.json`、`cover.webp`、`originals/`、`cache/`。
- 看过界面稿后问：「3D 翻阅的时候一页可以是多张图片吗，根据图片的长宽自动编排」。排版稿选 C：宽松、紧凑两档都要，可以切换。
- 看设计文档时问：「为啥要限制分册，一册 10000张图片有啥问题」。了解原因后（分册是为了让 3D 书不至于太厚），选 B：一本连续的书，不分册，3D 里只画固定厚度的一段，用页码滑条跳页。
- 看实现计划时说：「不需要trash 了，删除了就是删除了」。删除直接删文件，不留回收站。

假设（设计阶段已列出，用户没有异议）：

- 采用「相册墙 + 照片网格 + 3D 翻阅按钮」的结构。
- 一台电脑、一个用户、一个相册库。不做账号，不做云同步。
- 规模：几十本相册，每本几百张到一万多张，总共几万张以内。
- 浏览器：
  - 桌面：最新的 Chrome、Safari、Edge；
  - 手机：iOS Safari 16+、Android Chrome。
- 界面用中文；桌面优先，手机能用。
- 不写单元测试（用户偏好），仓库里不放测试文件。用以下方式验证：
  - 构建；
  - 仓库外的一次性检查脚本；
  - 无头 Chrome；
  - 真机清单。
- 卡册版（`cards.json` 占位卡）不再保留入口，代码留在 git 历史里（7a51e56）。

## 3. 范围

要做：

- **本地服务**（Node 内置 `http`）：提供网页、JSON 接口和图片。`npm start` 一条命令启动。
- **相册库**：目录结构和 `album.json`（§6）。
- **页面**（§9）：
  - 相册墙；
  - 相册页；
  - 选择模式；
  - 空相册 / 拖入上传；
  - 大图；
  - 3D 翻阅；
  - 手机访问。
- **导入**：
  - 来源：在电脑上选文件或拖入，在手机上从相册选；
  - 格式：JPG、PNG、WebP、HEIC 等；
  - 按内容去重；
  - 生成两种尺寸的缓存图。
- **管理**：
  - 新建、改名、删除相册；
  - 拖动排序（仅电脑）；
  - 设封面；
  - 删除照片（原图和缓存图直接删除，不能恢复）。
- **3D 翻阅**：
  - 一页多张自动排版，分「每页 1 张 / 宽松 / 紧凑」三档，每本相册记住自己的选择；
  - 整本相册是一本连续的书，不分册：3D 里只画 20 张活页，翻页时内容接着往后换；用页码滑条可以跳到任意一页；
  - 只给当前附近的页面生成贴图；
  - 点照片打开大图。
- **手机访问**：局域网链接、二维码、开关；链接里带随机密钥。

不做（留给子项目 2 或以后）：

- 授权码、试用、到期检查；Electron 安装包、自动更新、代码签名。
- Windows / Linux 上的 HEIC。本期只在 macOS 上用 `sips` 转码。
- 视频、实况照片的动态部分、照片说明文字、按拍摄时间排序、搜索、时间线。
- 照片在相册之间移动；编辑（裁切、旋转、滤镜）；手动调整 3D 排版。
- 回收站和撤销。删除就是删除，不能恢复。
- 多用户、外网访问。
- 窄屏单页模式。沿用卡册版的做法，手机竖屏时提示横过来。

## 4. 技术选型

- **前端**：沿用 Vite 8 + three 0.186 + 原生 JS，不用框架。
- **服务端**：
  - Node ≥ 20.9（本机为 v26）；
  - 只用内置模块（`http`、`fs`、`crypto`、`os`、`child_process`），外加 sharp。
- **新增依赖**：
  - `sharp` 0.35（运行时）：解码、按 EXIF 摆正、缩放、输出 WebP。它的预编译包不含 HEVC 解码，所以 HEIC 先用 macOS 自带的 `sips` 转成 JPEG。
  - `uqr` 0.1（前端）：把链接生成二维码 SVG，零依赖。
- **开发**：`npm run dev` 启动 Vite 开发服务器，同时挂上同一套接口（`vite.config.js` 里的插件在 `configureServer` 中挂中间件），只有一个进程。加 `--host` 后手机可以访问。
- **运行**：`npm start` 先 `vite build`，再 `node server/index.js`，在 5180 端口同时提供 `dist/` 和接口。
- **为子项目 2 留的接口**：服务端导出 `startServer()`，以后由 Electron 主进程直接调用。

接口：

- `server/app.js`：
  - `createHandler(lib)` 返回 `(req, res, next)`，`lib` 是 `openLibrary` 打开的相册库。它只处理访问控制、`/api/*` 和 `/media/*`，其他请求交给 `next`。开发时 `vite.config.js` 打开相册库后把它挂进 Vite；运行时由 `startServer` 使用。
  - `startServer({ dir, port = 5180, host = '0.0.0.0', dist })` 返回 `Promise<{ url, close() }>`，其中 `dir` 是相册库目录。它会：
    - 打开相册库；
    - 挂上 `createHandler`；
    - 提供 `dist/` 静态文件（`index.html` 不缓存，`/assets/*` 长缓存）。
- `server/library.js`：`openLibrary(dir)` 返回相册库对象：
  - 目录不存在时创建；启动时删除导入留下的临时文件。
  - 启动时扫描所有 `album.json`，建内存索引。
  - 读操作走内存。
  - 写操作按相册排队，依次执行。每次写盘先写 `album.json.tmp`，再改名为 `album.json`，保证原子性。
- `server/importer.js`：
  - `importPhoto(lib, albumId, stream, name)` 返回 `{ photo }` 或 `{ skipped: 'duplicate' | 'unsupported' | 'too-large' }`；
  - `ensureCache(lib, albumId, photo, size)`：缓存图缺失时现做。同一张图同时有多个请求时，只做一次。
- `src/book/layout.js`：
  - 保留 `DIM`；
  - 新增 `POCKET`（§10 的整页透明袋）；
  - `PER_PAGE = { 1: { avg: 1, max: 1 }, 2: { avg: 2, max: 3 }, 3: { avg: 3, max: 4 } }`；
  - `layoutPages(aspects, perPage)` 返回整本相册的页面数组。每页是 `{ rects: [{ i, x, y, w, h }] }`，`i` 是照片在整本相册里的序号，坐标是排版区内的 mm；
  - `photoAt(page, face, x, y)` 返回照片序号或 −1。
- `src/book/book.js`：`createBook(container, { title, pages, photoUrl, insets, startSpread, onChange, onPhotoClick })`：
  - `pages` 是整本相册的页面，书里只画其中 20 张活页的窗口（§11）；
  - 返回 `{ next(), prev(), toggleCover(), jump(spread), stats(), dispose() }`。`jump` 直接跳到第 spread 个跨页，不播翻页动画；`stats()` 返回 `{ offset, textures }`（窗口位置和现有贴图数），只给检查脚本用；
  - `photoUrl(i, size)` 返回第 i 张照片的图片地址；
  - `onPhotoClick(i)` 传出照片序号；
  - `onChange({ spread, spreads, closed })` 与卡册版相同，只是 `spread`、`spreads` 都按整本相册计算。
- `src/viewer.js`：`openViewer({ album, onOpenPhoto, onClose, onPerPage })` 返回 `{ close(), refresh(album) }`。
  - `onPerPage(perPage)` 在切换每页张数后调用，由相册页写入 `album.json`；
  - `refresh` 在相册数据变化后（例如在大图里删了照片）重新排版，并尽量停在原来的照片附近。

## 6. 相册库（数据结构）

位置：环境变量 `ALBUM_LIBRARY`，默认 `~/Pictures/相册库`。第一次启动时自动创建。

```
相册库/
├── library.json                     库设置
└── albums/
    └── 8f2a…（UUID）/
        ├── album.json               这本相册的全部信息
        ├── originals/               导入时复制进来的原图，永不修改
        │   ├── p001.heic
        │   └── p002.jpg
        └── cache/                   生成的缓存图，可以随时删掉重建
            ├── p001_600.webp        长边 600：网格、相册墙、3D 小图
            └── p001_1600.webp       长边 1600：大图、3D 大图
```

`library.json`：

```json
{ "version": 1, "phone": { "enabled": false, "key": "<32 位 hex>" } }
```

`album.json`：

```json
{
  "version": 1,
  "id": "8f2a…",
  "title": "2024 京都旅行",
  "createdAt": "2026-10-26T04:03:01.000Z",
  "cover": "p012",
  "perPage": 2,
  "nextSeq": 43,
  "photos": [
    { "id": "p001", "file": "p001.heic", "name": "IMG_2041.HEIC", "w": 3024, "h": 4032, "sha256": "…" }
  ]
}
```

规则：

- **顺序**：`photos` 数组的顺序就是显示顺序，网格和 3D 都按它排。
- **照片 id**：
  - 由 `nextSeq` 递增生成：p001、p002 …，超过 999 时自然变成四位；
  - 删除后不再复用，所以图片地址可以永久缓存。
- **尺寸**：`w`、`h` 是按 EXIF 摆正后的尺寸，排版用它的宽高比。
- **封面**：`cover` 是照片 id；`null` 表示用第一张。删除封面照片后，`cover` 自动变为 `null`。
- **每页张数**：`perPage` 取 1 / 2 / 3，分别对应「每页 1 张 / 宽松 / 紧凑」，默认 2。
- **相册墙顺序**：按 `createdAt` 倒序，新建的在前。
- **删除不能恢复**：没有回收站，删除就是直接删文件。
- **删照片**：
  1. 先写 `album.json`；
  2. 再删除原图和两张缓存图。如果第 2 步途中程序退出，会留下没人引用的文件，只占空间，不影响使用。
- **删相册**：先把文件夹改名为 `albums/.del-<相册id>`，相册立刻从列表里消失；再删除整个文件夹。
- **启动清理**：`openLibrary` 删除导入留下的临时文件 `.tmp-*`，以及没删完的 `.del-*` 文件夹。没被 `album.json` 引用的其他残留文件不影响使用；导入中断留下的文件，下次取号时会被同名文件覆盖。

相对用户参考结构的改动：

- `library.db` 改为 `library.json`，再加上启动时扫描 `album.json` 建的内存索引。原因是数据量小，文件可读、好备份，也不用引入 SQLite。以后要做搜索或时间线时，再加一个可以从 `album.json` 重建的数据库。
- 去掉 `cover.webp`：封面直接用那张照片的缓存图。
- `cache/` 存两种尺寸。

## 7. HTTP 接口

请求和响应都是 JSON（上传除外）。出错时返回 4xx/5xx 和 `{ "error": "…" }`。`/api/*` 一律 `Cache-Control: no-store`。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/albums` | 相册列表 `[{ id, title, count, cover: { id, w, h } \| null, createdAt }]`，新建的在前 |
| POST | `/api/albums` | `{ title }` → 新相册。title 去掉首尾空格后为 1–50 字，否则返回 400 |
| GET | `/api/albums/:id` | `album.json` 的内容 |
| PATCH | `/api/albums/:id` | `{ title?, cover?, perPage?, order? }` → 改后的相册。`order` 必须正好是当前所有照片 id 的一个排列，否则返回 409，前端会重新加载 |
| DELETE | `/api/albums/:id` | 删除整本相册，文件夹一起删除 |
| POST | `/api/albums/:id/photos?name=<文件名>` | 请求体就是文件本身，一次一张，请求头带 `X-Album-Upload: 1`。返回 `{ photo }` 或 `{ skipped }` |
| POST | `/api/albums/:id/photos/delete` | `{ ids }` → 改后的相册；原图和缓存图一起删除 |
| GET | `/media/:albumId/:photoId/600`、`/1600` | WebP 缓存图，缺了就现做；带 `Cache-Control: public, max-age=31536000, immutable` |
| GET | `/media/:albumId/:photoId/original` | 原图，`Content-Disposition: inline`，文件名用原来的名字 |
| GET | `/api/phone` | `{ enabled, key, ip, port }`，只允许本机调用 |
| PATCH | `/api/phone` | `{ enabled }`，只允许本机调用。每次打开都生成新密钥，旧链接随之失效 |

几点说明：

- 上传不用 multipart。前端对每个文件调用 `fetch(url, { method: 'POST', body: file })`，按顺序一张一张传。这样服务端可以边收边写盘，前端也有天然的逐张进度。
- 其余写接口的请求体是 JSON，要求 `Content-Type: application/json`（原因见 §12）。
- `port` 取 `req.socket.localPort`。所以开发时（Vite 端口）和运行时（5180）都正确。
- 前端用 `location.hostname` 是否为 `localhost` / `127.0.0.1` 判断是否在本机，决定是否显示「手机访问」。

## 8. 导入流程

`importPhoto` 处理一张照片的步骤：

1. `Content-Length` 超过 100 MB 时直接返回 `too-large`。否则边把请求体写进临时文件 `originals/.tmp-<随机>`，边算 sha256、数字节，超过 100 MB 就中止并返回 `too-large`。
2. 进入这本相册的写队列。后面的步骤依次执行，避免两台设备同时传同一张。
3. 与本相册已有照片的 sha256 比较，相同则删除临时文件，返回 `duplicate`。
4. 取号 `pNNN`（`nextSeq`）。
5. 识别格式：只收位图照片（sharp 识别为 jpeg、png、webp、gif、tiff、heif）。其他格式（如 SVG，里面可以带脚本）返回 `unsupported`。
   解码：先交给 sharp。sharp 不能解码时，如果是 macOS，就用 `sips -s format jpeg` 转成临时 JPEG（`.tmp-*`，用完即删）再交给 sharp，这条路径处理 HEIC。仍然失败则返回 `unsupported`。
6. 用 sharp `.rotate()` 按 EXIF 摆正，得到摆正后的 `w`、`h`。
7. 生成两张缓存图：`cache/pNNN_600.webp`（长边 600，质量 80）和 `cache/pNNN_1600.webp`（长边 1600，质量 82），都不放大。
8. 临时文件改名为 `originals/pNNN.<扩展名>`。扩展名按识别出的格式取：`.jpg`、`.png`、`.webp`、`.gif`、`.tif`、`.heic`（AV1 编码的 heif 用 `.avif`），不用原文件名里的扩展名。`name` 只取文件名部分，最多 200 字。
9. 把照片追加到 `photos` 末尾，`nextSeq + 1`，写入 `album.json`。到这一步才算导入成功。

缓存图缺失时（例如手动删了 `cache/`），`ensureCache` 从原图按第 5–7 步重新生成。

## 9. 页面与交互

路由（hash），浏览器的返回键可以关闭大图和 3D：

| 地址 | 页面 |
|---|---|
| `#/` | 相册墙 |
| `#/a/<id>` | 相册页 |
| `#/a/<id>/p/<photoId>` | 相册页 + 大图 |
| `#/a/<id>/3d` | 相册页 + 3D 覆盖层 |
| `#/a/<id>/3d/p/<photoId>` | 3D + 大图 |

只改变地址末尾时（例如打开大图），下面的页面保持不动。页面重新获得焦点时会重新拉取数据，这样手机上传的照片在电脑上也能看到；3D 打开时不自动刷新，免得正在看的书被重建。

## 10. 3D 自动排版

**页面**：活页尺寸沿用 `DIM`（209.8 × 192.4 mm），每面改为一个整页透明袋（`POCKET`）：

- 边距：靠环一侧 22 mm，外侧 5.6 mm，上下各 6.4 mm，所以袋子是 182.2 × 179.6 mm；
- 袋内留白 5 mm，照片间距 4 mm；
- 排版区为 172.2 × 169.6 mm。

**一页内怎么摆**：

- 照片顺序不变；不裁切，每张都按原比例完整显示。
- 把这页的照片用「左右并排」和「上下叠放」两种切分递归组合成切分树。枚举所有保持顺序的切分树（4 张以内最多 40 种），取铺满率最高的一种。
- 多张照片时，只要有一张短边小于 30 mm，这种摆法就不要。整组在排版区里居中。
- 每棵树的宽都是高的一次函数 `w = a·h + b`（含间距），所以可以精确计算：
  - 叶子：a = 宽高比，b = 0；
  - 并排：a = a₁ + a₂，b = b₁ + b₂ + 4；
  - 叠放：a = 1 / (1/a₁ + 1/a₂)，b = a·(b₁/a₁ + b₂/a₂ − 4)；
  - 放进排版区：h = min(169.6, (172.2 − b) / a)，然后从上往下算出每张照片的矩形。

**每页几张**（`perPage`）：

| perPage | 名称 | 平均每页 | 每页上限 |
|---|---|---|---|
| 1 | 每页 1 张 | 1 | 1 |
| 2 | 宽松（默认） | 约 2 | 3 |
| 3 | 紧凑 | 约 3 | 4 |

**分页**：

- 整本相册的照片按顺序排成一串连续的页面，不分册。
- 为了算得快，照片按顺序每「40 × 平均每页」张（40 / 80 / 120 张）分成一段，每段约 40 页，单独排版后接起来。一页不会跨段，所以看不出段与段的分界。
- 一段有 m 张照片时，页数 P = ⌈m / 平均每页⌉。最后一段如果 P 是奇数且 P < m，就加 1，让最后一张活页的背面不空着。
- 用动态规划在「正好 P 页、每页不超过上限」的所有分法里，选总铺满率最高的一种。如果因为 30 mm 的限制排不下（例如连着很多超长全景图），就把 P 加 1 再排。单张一页总是可行的，所以一定能排出来。
- 排版结果只由照片顺序和宽高比决定，不存盘。在相册末尾加照片，只有最后一段的排版会变；在中间插入或调整顺序，从那一段往后都会变。
- 原型数据（排版稿用的是同一算法）：
  - 平均铺满率（2400 张随机横竖混合照片）：每页 1 张约 72%，宽松约 84%，紧凑约 92%；
  - 宽松档多是「一张一页」和「一大配两小」交替。因为页面接近正方形，两张一页留白最多；
  - 1 万张照片分段排版（本机 Node）：每页 1 张 7 ms，宽松 22 ms，紧凑 79 ms。

**点击命中**：

- `photoAt(page, face, x, y)`：照片矩形在面上的位置 = 袋子左上角 +（5, 5）+ 排版区坐标。
- 偶数面（右页）的袋子从 x = 22 开始，奇数面从 x = 5.6 开始，与卡册版的 `pocketRect` 一致。

## 11. 3D 贴图与性能

- **每面的绘制**（`textures.js`），风格沿用卡册版的 PVC：
  - 膜底色；
  - 整页袋的焊缝、袋口亮边和阴影；
  - 照片：0.6 mm 圆角，带轻微投影；
  - 孔。
- **图片尺寸**：照片在页面上的长边超过 150 mm（贴图 4 px/mm，相当于超过 600 px）时用 1600 图，否则用 600 图。图片画进画布后就丢掉 `Image` 对象。
- **占位**：图片没到或加载失败时，画浅灰色占位。
- **懒贴图**：
  - 贴图按整本相册的页号缓存。只给当前跨页和前后各 2 个跨页（最多 10 面）建贴图；其他面共用一张只有膜和孔的空白贴图；
  - 翻页或挪窗口后，由 `book.js` 补建新进入范围的贴图（直接替换 `material.map`），并释放离开范围的；
  - 快速连翻时，远处的页面会先显示空白，随后出现照片。
- **重建**：切换每页张数、`refresh` 时，销毁整本书（`dispose`）后按新的页面重建，并用 `startSpread` 停在原来的照片附近。滑条跳页不重建。

**一本连续的书（滑动窗口）**：

按真实厚度画，书会随活页数变厚。实测（每页约 2 张，电脑 1280 宽屏幕上一页的宽度）：

| 活页 | 照片约 | 书厚 | 一页宽度 |
|---|---|---|---|
| 20 | 80 | 2 cm | 463 px |
| 100 | 400 | 10 cm | 301 px |
| 2500 | 10000 | 2.6 m | 26 px |

2500 张活页时，每帧还要画约 7500 次。所以 3D 里只画固定的一段：

- **窗口**：整本相册共 G = ⌈页数 / 2⌉ 张活页、G + 1 个跨页。3D 里只画 S = min(20, G) 张活页，对应整本里从第 o 张开始的连续 S 张。书厚和环的大小都按 S 计算，所以 G ≥ 20 时书始终是 2 cm 厚（R = 21 mm）。
- **跨页号**：整本的跨页号 = o + 卡册版 `book.js` 里的 k；合上时（k = 0）为 0。`onChange` 报整本的跨页号和 G + 1。
- **保持居中**：每一帧，只要没在拖动，就计算目标位置 o′ = clamp(跨页号 − 11, 0, G − S)，也就是左右各 10 张（相册开头和结尾除外）。如果 o′ ≠ o，而且要移出窗口的活页都已静止，就挪动窗口：
  - 各活页的动画状态整体平移 o′ − o 位；新进入窗口的活页在它所在的一侧静止放好；
  - 每张活页的贴图改指向它现在对应的页（贴图按页号缓存，不用重画）；
  - 当前跨页的内容不变，左右两叠各增减 |o′ − o| × 1.05 mm。平常翻一页只差约 1 mm。
- **翻到窗口边上**：翻页前先试着挪窗口。要移出的活页还在动、挪不了时，这次翻页先不执行（快速连按时会稍微停一下）。
- **跳页**（滑条、`startSpread`）：直接把窗口和 k 放到目标位置，所有活页静止，不播翻页动画。
- **合上**：沿用卡册版，从任何位置合上后再打开，都回到第一个跨页（窗口回到开头）。如果合上后窗口还没回到开头就又打开，直接跳到第一个跨页。
- **小相册**：G ≤ 20 时 o 始终为 0，行为和卡册版完全一样。

## 12. 访问控制与安全

服务监听 `0.0.0.0`，按请求来源区分：

- **本机**（127.0.0.1、::1、::ffff:127.0.0.1）：不需要密钥。
- **其他地址**：
  - 手机访问关闭时，返回 403 页面：「手机访问已关闭，请在电脑上打开「手机访问」」。
  - 手机访问开启时，第一次访问带 `/?key=…`。服务端校验通过后，设置 Cookie `album_key`（HttpOnly、SameSite=Lax、一年有效），页面照常返回，地址里保留 key：从微信跳到 Safari、从主屏幕图标打开时都还没有 Cookie，要靠地址里的 key。之后的接口和图片请求靠这个 Cookie。密钥不对返回 403。
  - `/apple-touch-icon.png` 不需要密钥：iOS 取主屏幕图标时可能不带 Cookie。
  - 校验用 `crypto.timingSafeEqual`。密钥是 128 位随机数。
- **`/api/phone`** 只允许本机调用。
- **路径安全**：
  - 路径参数先校验格式：相册 id 必须是 UUID，照片 id 必须是 `p` 加数字，尺寸只能是 600 / 1600 / original，否则返回 404。
  - 照片 id 还必须在 `album.json` 里，文件路径由 `album.json` 里的 `file` 拼出，不直接用请求里的字符串。
  - 静态文件的路径规范化后必须仍在 `dist/` 内。
  - `/media/*` 响应都带 `X-Content-Type-Options: nosniff` 和 `Content-Security-Policy: sandbox`：不管文件里是什么，都不会在本站里当网页运行。
  - 发送文件前先打开文件：文件在这之间被删除或读不了时返回 404，不会让服务退出。
- **防跨站与 DNS 重绑定**（因为本机请求不要密钥，必须防止网页借用户的浏览器调用本机接口）：
  - `Host` 必须是 `localhost`、`127.0.0.1` 或本机的局域网 IP（带端口），否则返回 403。
  - 写请求（POST / PATCH / DELETE）如果带 `Origin` 头，它必须与 `Host` 一致，否则返回 403。
  - JSON 接口要求 `Content-Type: application/json`，上传要求带 `X-Album-Upload: 1` 头。这样跨站请求都需要预检，而服务端不响应 CORS，预检就会失败。
- **已知限制**：局域网里走的是 HTTP，没有加密，只适合家里或可信的 Wi‑Fi。弹窗里不展开说明。
- 开发模式下，同一套检查作为 Vite 中间件运行，排在 Vite 自己的中间件前面。

## 13. 错误处理

- **启动**：
  - 相册库目录不能创建或不可写：打印原因后退出；
  - 端口被占用：提示「端口 5180 被占用，可以用 PORT=xxxx npm start 换一个」后退出。
- **相册数据**：某本相册的 `album.json` 损坏或读不了时，列表里跳过这本，在终端打印警告，不影响其他相册。
- **接口出错**：前端用轻提示显示「操作失败：…」，界面保持原状态。如果是 409（排序冲突），重新加载这本相册。
- **上传**：网络失败的照片计入「失败 d 张」，重新上传即可，已传上的会被当作重复跳过。
- **图片**：
  - 缓存图缺失时现做；
  - 原图也缺失时返回 404。网格和大图显示灰色的「图片丢失」，3D 里画浅灰占位。
- **3D**：WebGL 不可用时，沿用卡册版的提示（文案改为「相册」）。
- **手机访问**：拿不到局域网 IP 时，弹窗显示「这台电脑没有连接局域网」，开关不可用。

# 相册里混排视频 设计文档

- 初稿日期：2026-10-28；技术修订：2026-10-30。
- 状态：本地功能实现与源码、桌面、成品自动化已完成，进入整分支审查；其他目标设备边界见第 8 节。
- 源码基线：`feat/video-in-albums` / `d48b77666e2de4e77c0f80b80ff87776bcbbc264`。保留现有照片、Details、备注、许可证与手机访问行为。
- 基础：本地相册管理设计、Folio 界面改版设计，以及已提供的混排 UI 稿。UI 稿中的导入和数据操作是模拟，不是实现验收。

## 1. 目标与约束

同一本相册混排照片和视频，一起排序、设封面和删除。网格与 3D 书显示视频封面帧，点开后使用原生视频控件播放；不会播放的设备仍能查看封面、信息与备注。

沿用已经确认的方向：

- 不转码、不换封装，不打包 ffmpeg 或新增编解码器。原视频逐字节保存。
- 封面帧、视频显示尺寸和时长由导入设备的浏览器准备，与原文件一次上传。导入设备必须成功解码并取得封面，不能只凭扩展名收下文件。
- 只接收 MP4、MOV、M4V 这一组 ISO BMFF 视频容器；不收 WebM、实况照片动态部分。
- 视频上限明确为 **1 GB = 1,000,000,000 字节**，不另外限制时长。照片的原有限制不变。
- 播放能力取决于查看设备的实际解码支持，不能从 MOV、HEVC 名称或硬件型号推定。不能播放时只显示封面与说明，不增加系统播放器或云端兜底。
- 只做前台顺序导入；不做并行解码、续传、重启恢复上传、额外的后台任务系统。
- 3D 书不播放视频，相册墙预览不加播放标记。
- 保持 JSON 相册库，不增加数据库。保留现有沙箱、CSP、导航限制、离线授权和只读查看/备份能力。

本轮修订明确改变旧稿中五处约定：不再把未知 `ftyp` 当作 MP4；不再把缩小的封面尺寸当原视频尺寸；MOV 使用真实 MIME；原生控件优先而不是按底部 56px 猜控制区域；超时和读取失败不统一叫「格式不支持」。

## 2. 用户界面

沿用已展示的 UI 方向，不重做桌面整体设计：

- 混排网格保留图片比例，视频增加播放标记与时长；支持混合选择、排序、设封面与批量删除。
- 桌面 lightbox 使用媒体区与默认打开的浅色 Details；手机保持媒体优先、紧凑摘要与可收起信息。
- 视频播放器使用系统原生进度、音量和全屏控件，不制作另一套播放器。
- 导入显示「准备视频 → 上传 → 保存 → 完成」，有清楚的文件名与失败原因。
- 同一条视频也只有一条可编辑备注，复用现有保存、冲突检测、取消、清空和未保存导航保护。
- 中英文、长文件名和 320px 窄窗口不得造成横向溢出。

## 3. 数据契约

### 3.1 相册条目

继续使用 `album.photos`、`pNNN` 编号、现有排序/封面/删除接口与相册版本 1。只有 `kind === 'video'` 才走视频分支；没有 `kind` 的旧照片无需迁移。

```json
{
  "id": "p012",
  "kind": "video",
  "file": "p012.mov",
  "poster": "p012-poster.jpg",
  "name": "IMG_0420.MOV",
  "w": 3840,
  "h": 2160,
  "posterW": 1600,
  "posterH": 900,
  "duration": 12.4,
  "sha256": "视频原始字节的 SHA-256",
  "metadata": {
    "schemaVersion": 1,
    "kind": "video",
    "format": "mov",
    "bytes": 12500000,
    "dimensionsSource": "browser",
    "durationSource": "browser",
    "fileModifiedAt": "2026-10-28T08:30:00.000Z",
    "fileTimeSource": "source-file"
  }
}
```

- `w/h` 是浏览器 `videoWidth/videoHeight` 报告的原视频显示尺寸，包含浏览器处理的旋转，不是缩小后的封面或未经旋转的编码像素矩阵。
- `posterW/posterH` 由服务器读取实际 JPEG 得出，最长边不超过 1600，排版仍使用 `w/h` 的显示宽高比。
- `duration` 保存浏览器报告的有限正数秒，不在入库时四舍五入成一位小数，避免极短视频变成 0。界面另行格式化。
- 尺寸与时长仅作显示，服务器做数值边界检查，不声称独立核验视频的分辨率、时长或编码。来源字段明确这一点。
- `bytes` 由服务器统计视频部分的实际字节数；`format` 来自容器检查，不信任文件名或客户端 MIME。
- 文件修改时间来自合法的 `File.lastModified`，不是拍摄时间。没有合法来源时，两个文件时间字段均为 `null`，不拿导入时间冒充。
- `metadata` 的 `kind` 区分视频与既有照片 schema。视频不填 `exifStatus`、相机、GPS 或拍摄时间，不交给照片 EXIF 解析器。
- 原视频与 JPEG 封面保存在 `originals/`，600/1600 WebP 是可再生缓存。可选 `note` 的语义与照片一致。

### 3.2 列表与计数

`list()` 保留总 `count` 与现有预览结构，增量返回 `photoCount`、`videoCount`，且二者之和等于 `count`。只有视频条目计入 `videoCount`。

相册、相册墙和首页的动态统计同步使用分类计数，不把视频计成照片；无视频时保持原有照片文案。首页宣传文案不变，相册墙仍只显示缓存封面，不增加播放标记。

### 3.3 Details 与备注

保留 `GET /api/albums/:id/photos/:photoId/details`。照片响应不变；视频响应增加 `kind: 'video'` 并返回视频 metadata，不触发 `readPhotoMetadata()`。

视频 Details 展示文件名、格式、显示分辨率、服务器记录的大小、时长与可用的文件修改时间。格式/分辨率/大小只在摘要显示，不在展开区重复堆叠。不展示照片的「无 EXIF」提示。视频 metadata 缺失或不合法时，只对原文件 `stat` 补充可得的大小，不解码视频或改写相册。

备注继续使用原 PATCH 路由、2,000 Unicode 码点上限与 `previousNote` 并发检测。异步 Details、封面设置或媒体切换不能覆盖较新的备注，也不能绕过未保存/正在保存保护。

## 4. 上传与存储

### 4.1 请求与返回值

沿用 `POST /api/albums/:id/photos` 和 `X-Album-Upload: 1`。无 `kind` 时保持照片上传；显式但未知的 `kind` 返回 `unsupported`，不降级成照片。

视频参数：

| 参数 | 含义与边界 |
| --- | --- |
| `kind=video` | 显式选择视频协议 |
| `name` | 原文件名，沿用 basename 与长度清理，不作为磁盘路径 |
| `posterBytes=N` | 十进制正整数，`1..10,485,760`，即最多 10 MiB |
| `w`、`h` | 浏览器报告的显示尺寸，各为十进制整数 `1..65,535`；不是服务器解码分配尺寸 |
| `duration` | 十进制有限正数秒，可使用科学计数法；缺失、空白、0、NaN、Infinity 均拒绝 |
| `lastModified` | 可选，沿用毫秒时间戳；只接受安全整数 `0..253402300799999`，非法值不展示为文件时间 |

请求体为 `new Blob([poster, file])`，即前 N 字节 JPEG，后续字节全部为视频原文件，不把整个请求读入内存。视频大小和 SHA-256 都只计算后半段。

返回形状与照片保持一致：

- 成功：`{ photo: videoItem }`，仍使用 `photo` 兼容当前调用方。
- 已存在相同视频字节：`{ skipped: 'duplicate' }`，不因封面不同而另存一份。
- 视频超限：`{ skipped: 'too-large' }`。
- 参数、封面或容器不符合协议：`{ skipped: 'unsupported' }`。
- 授权、相册不存在、存储失败等继续使用现有非 2xx 错误，不伪装成不支持的格式。

### 4.2 有界接收

先通过 Host、手机访问、同源、许可与上传头校验，再创建临时文件。按流累计消费 JPEG 和视频，正确处理分界跨任意 chunk；body 比 N 短或没有视频部分均拒绝。

可信的 `Content-Length` 超过 `N + 1,000,000,000` 时提前拒绝；没有此头仍按实际视频字节持续限流，恰好上限允许。写入需遵守 backpressure，不能累积整个视频或大量未完成的写操作。

提前拒绝/流式超限后停止写盘，清理本任务文件；连接仍可用时先发送对应 JSON 并设置 `Connection: close`，响应结束后关闭未消费连接，不无限排空攻击性请求。请求已经中断时按中断处理，不承诺仍能送达 JSON。不能在发送响应前自动销毁请求流，导致正常超限只有无说明的 socket reset。

现有 HTTP 接收超时和应用退出策略继续生效；大小上限不是保证任意慢的网络都能完成。超时/断网说明可重新选择后重试，不提供续传。

### 4.3 容器与封面校验

容器检查只确认有限结构，不做视频解码或完整媒体正确性验证：

1. 第一个 box 必须是完整 `ftyp`；尺寸至少容纳 major brand 与 minor version，兼容品牌区长度必须是 4 的倍数，整个 `ftyp` 最多 4 KiB。
2. major brand 白名单为 `qt  `、`M4V `、`M4VH`、`M4VP`、`isom`、`iso2` 至 `iso9`、`mp41`、`mp42`、`avc1`、`hvc1`、`hev1`。未知 major brand 不默认当成 MP4。
3. major 或兼容品牌含 HEIF/AVIF 图片品牌时拒绝，包括 `mif1`、`msf1`、`miaf`、`heic`、`heix`、`hevc`、`hevx`、`heim`、`heis`、`hevm`、`hevs`、`avif`、`avis`。
4. 遍历顶层 box，并只深入 `moov/trak/mdia` 检查 `hdlr` 的 `handler_type === 'vide'`。必须存在至少一个这样的视频轨与非空 `mdat`；只含音轨或图片不能通过。
5. 32/64 位长度、父子范围与文件边界必须合法；扩展长度用不会丢精度的整数检查。size=0 仅允许占满其所属范围的最后一个 box。拒绝不足 header、越界、溢出和无法推进的 box。
6. 最多检查 4,096 个 box header，累计实际读取的结构数据最多 512 KiB；按偏移跳过大 `mdat` 和无需解释的 payload，不把完整 `moov` 或媒体读进内存。超出检查预算按 `unsupported` 处理。
7. `qt  ` 保存为 `.mov`，三个 `M4V` 主品牌保存为 `.m4v`，其余白名单保存为 `.mp4`。不修改视频字节。

这能拦住现有 HEIC 夹具、音频容器和明显损坏的 box，不等于保证样本表、每一帧或某台设备的 codec 可用。浏览器实解码成功仍是正式客户端导入的前提。

封面必须确为单幅 JPEG，不接受其他 sharp 可读格式冒充 JPEG。先用有像素限制的 metadata 读取验证正尺寸、最长边 ≤1600、像素数 ≤2,560,000，再完整解码生成缓存；损坏图拒绝。10 MiB 字节上限和像素上限同时生效，不按客户端报告尺寸分配解码内存。

### 4.4 提交与失败一致性

本次上传拥有独立随机 `.tmp-*` 视频和 JPEG 路径。流接收与基础验证完成后，进入现有相册队列：

1. 再次读取相册，避免排队期间被删除；按视频 SHA-256 去重。
2. 从 `nextSeq` 起分配未占用编号：不仅检查索引，也检查该编号已有的原文件、poster 和缓存，不能覆盖上次崩溃留下的正式文件。
3. 用 JPEG 生成 1600/600 WebP。记录本任务创建的缓存和已改名路径，以便补偿。
4. 把视频和 JPEG 分别改名为正式名称；最后通过现有原子 JSON 保存写入新条目和新的 `nextSeq`。只有这一步成功才提交并返回成功。
5. JSON 提交前发生任何失败，包括缓存、第二次改名、相册消失或 JSON 保存失败，清理本次任务的临时文件、已改名文件和缓存。清理不能误删旧条目，不因一个清理失败而停止其余清理；无法清理的路径记录错误。
6. JSON 已提交后不再因响应发送失败回滚文件。客户端断线不等于已接受写入必须撤销；重新加载相册可看到已经提交的项目。

不宣称多个文件与 JSON 构成断电原子事务。启动时继续清理 `.tmp-*`；突然崩溃可能留下未被索引引用的正式文件，它们不会出现在相册或媒体路由中，后续编号不得覆盖。不增加删除所有未知文件的扫描，也不承诺自动找回这类文件。要实现跨断电自动回滚需另行设计日志，不在本轮范围。

删除仍先保存索引，再清理被删条目的原视频、JPEG 和两个缓存；正常完成后这些文件均不存在。系统占用/断电导致的删除残留遵循现有相册库边界，不再通过媒体路由暴露。

`ensureCache()` 对视频只从 `poster` 重建 WebP，不尝试由服务器解码原视频。JPEG 也缺失时，缩略图返回现有缺失响应，但原视频接口与播放器不因此禁用。

### 4.5 原文件读取

沿用 `/media/:album/:id/original`、`/600` 和 `/1600`。原视频使用现有单段 Range 路径，并验证完整/开放/后缀范围、206、416 和 HEAD；断开请求必须关闭文件句柄。

MIME：`.mp4` 和 `.m4v` 为 `video/mp4`，`.mov` 为 `video/quicktime`。不以改 MIME 冒充换封装或保证解码；原文件安全响应头、手机 gate 与同源限制不变。现有 `media-src 'self' blob:` 已满足需求，不放宽 CSP 或桌面导航策略。

## 5. 浏览器准备与上传

### 5.1 选择与队列

选择框增加 `video/mp4,video/quicktime,video/x-m4v,.mp4,.mov,.m4v`；拖放和手机选择进入现有顺序队列。MIME/扩展名只用于分支选择，不作为服务端识别依据。

保留照片原上传路径。视频先检查文件大小，再准备封面，最后上传；同一时间只有一个视频 probe。某个项目失败应释放资源并继续队列，不让后续照片一起失败。

### 5.2 `probeVideo`

新增 `src/video-probe.js`，接口为 `probeVideo(file, { signal } = {})`，返回 `{ poster: Blob, w, h, duration }`。

1. 创建 Blob URL 与临时原生 `<video muted playsinline preload="auto">`，设置监听和 15 秒总 deadline 后再设置 src/load。元素可离屏但不依赖 `display:none` 或先等待 `loadeddata` 才触发加载。
2. 立即尝试受控静音 `play()` 以促使解码，与 metadata/错误监听并行。若策略拒绝但加载仍能得到可用帧则继续；否则明确报告准备受限，不把拒绝直接当作 codec 不支持。
3. metadata 到达后验证有限正 duration 和合法显示尺寸，暂停并 seek 到 `min(1, duration / 2)`；先挂 `seeked` 监听，不等待不可能再触发的事件。
4. 确认解码帧就绪再画图；支持时使用 `requestVideoFrameCallback`，必要的静音播放仍受同一个 deadline 限制。其他环境用媒体就绪状态与事件兜底，不只检查 `canPlayType()` 或文件头。
5. 用原显示尺寸计算缩放，最长边 ≤1600 且不放大；canvas 导出 JPEG、质量 0.85，检查非空 Blob 与字节上限。
6. 成功、异常、超时或取消都撤销监听/帧回调/计时器，pause、清源、load、移除元素并释放 Blob URL。旧异步任务不得在释放后继续播放或回写 UI。

准备错误至少区分 `unsupported`（明确不支持或无法解码）、`timeout`、`blocked`（播放策略阻止准备）、`unreadable`（文件/截帧失败）和 `AbortError`。超限直接用 `too-large`，不启动 probe。没有成功封面的项目不发上传请求；取消不冒充失败或不支持。

### 5.3 XHR 与进度

`api.uploadVideo(albumId, file, probe, onProgress, { signal } = {})` 使用 XHR、同源认证与上传头，body 为 JPEG+原文件 Blob，不先把整个视频读取成 ArrayBuffer/Base64 或构造整文件副本。监听进度、load、网络错误、abort，并清理所有监听。

上传字节到 100% 后切换「保存中」，只有收到成功 JSON 才计入已导入。网络中断、非 2xx 和不合法响应不显示成功；服务端返回的 duplicate/unsupported/too-large 沿用跳过统计。

从开始准备到服务器返回，整个队列一直保持 `data-busy`。继续阻止语言/相册库切换，并阻止离开正在导入的相册；先保留原有备注导航保护。销毁页面时取消未完成 probe/XHR、清空后续队列，finally 恢复 busy，不回写已销毁节点。

前端的「准备中」不是服务器已接受写入。服务器正常退出继续 drain 已收到的写请求；完整 body 已接收后的提交不因客户端离开而留下半条记录。许可证按现有请求入口校验；已过期不能开启新写入，既有读取与备份仍可用。

## 6. 浏览、播放与交互

### 6.1 网格和 3D

网格用 600 缓存显示视频封面，叠加播放图标与时长。时长显示 `m:ss`，超过一小时为 `h:mm:ss`，不足一秒显示 `0:00`，不改变实际存储值。

`createBook` 增加可选 `itemInfo(i)`，返回 `{ kind, duration }`；现有照片调用方不必传。书页在封面上绘制播放标记与时长，不创建 video 或加载视频原文件。布局使用原视频显示宽高比，沿用 `onPhotoClick` 打开 lightbox。

### 6.2 Lightbox

视频项使用 `<video controls playsinline preload="metadata">`；poster 为 1600 缓存，src 为原文件。进入时可尝试一次有声播放；`NotAllowedError` 保留正常的暂停/手动播放状态，不显示损坏或不支持。

媒体错误处理：

| 情况 | 展示与恢复 |
| --- | --- |
| code 4 / NotSupportedError | 保留封面，先用同源 HEAD 有界确认原文件可读，再提示「此设备无法播放这个视频」；原文件 404/403/网络失败属于读取失败 |
| code 3，解码失败 | 保留封面，提示「无法解码这个视频」，不称为图片丢失 |
| code 2，网络/读取失败 | 保留可用封面，提示读取失败，可重试 |
| code 1，主动取消或旧任务 | 当前代际仍有效的非主动中断才提示；主动清理不显示错误 |
| 仅 poster 缺失 | 保留播放器与原文件入口，仍尝试加载视频 |

实施期实测补充：Chromium 对原文件 HTTP 404 也可能报告 code 4，因此不能单凭它断言设备 codec 不支持。每个失败的播放器只发起一次 HEAD，最多等待 5 秒；切换/关闭会取消，迟到结果不得影响其他项目。这不增加视频解码或新读取权限。

每次切换、关闭、当前项删除或页面销毁，先让旧请求身份失效并移除监听，再 pause、清源、load。迟到的 error、帧回调和 play Promise 不得影响新项目。相同项目因备注或封面状态刷新时，不无故重建播放器、回到开头或重复自动播放。

相邻项目只预加载封面，不预加载视频。视频原文件按钮显示「原文件 / Original file」，沿用已有受限新窗口路径，不呼出系统播放器。

### 6.3 原生控件优先

不按「底部 56px」猜测控件位置。视频元素及其原生控件上的 pointer/swipe 都不触发相册翻页；翻页使用显式上一项/下一项按钮或播放器外的空白区域。

键盘焦点在 video/原生控件、输入框或可编辑文字时，方向键交给它们，不交给下层 3D 书。其他区域的方向键仍可翻页。处于原生视频全屏时，Escape 优先退出全屏；非全屏才按现有备注、Details、lightbox 的顺序处理退出。

## 8. 验证

### 8.1 服务端与模型

- 各种 chunk 分界、body 短于 N、空视频、缺失/非法参数；10 MiB JPEG 与 1 GB 视频的临界值。超限用注入小上限测试，不在 CI 生成 1 GB 文件。
- HEIC/AVIF、未知品牌、纯音轨、截断和越界 box、32/64 位长度及检查预算。有效白名单 MP4/MOV/M4V 均保留源字节和视频 SHA-256。
- 非 JPEG、超大像素、损坏封面；客户端假尺寸不控制服务器解码分配。
- 不同 poster 的同视频去重；并发排序/备注/删除、排队中相册消失、nextSeq 占用和旧照片无 kind 的兼容。
- 接收中断、写盘、缓存、两次改名、JSON 保存各阶段故障后的任务文件清理；模拟崩溃残留不会被下一次上传覆盖。补偿不删除既有条目。
- 视频作为封面、混合排序/删除、列表分类统计、JPEG 重建缓存、JPEG 缺失时原文件仍可读。
- 正常/开放/后缀 Range、206/416、HEAD、停止下载、Windows 文件句柄释放；Host/手机访问保护、无效与过期许可阻止写入但保留读取。
- 视频 Details 不调用照片 EXIF，不写入虚构相机或拍摄时间；备注 CAS 与只读行为保持。

### 8.2 浏览器和真实 Electron

用小型、自有、可追溯的 H.264/AAC 与无音轨样片写聚焦用例，不在测试运行时要求 ffmpeg。生成命令与来源随夹具记录，应用不获得新的 codec 依赖。

- probe 实际解码、seek、JPEG 帧、原显示尺寸与缩小封面分别验证；不把 `canPlayType()` 或 currentTime 赋值当成解码成功。
- 超时、策略拒绝、损坏/不支持、取消和重复多文件准备均正确释放资源、恢复队列状态。
- 一次混排导入、网格标记/分类计数、播放器真实时间前进/帧解码、原生方向键/拖动、切换释放与旧事件隔离。
- 备注/设封面刷新不重启视频；未保存保护、只读模式、重启后持久化、中英文与窄屏布局。
- 3D 只使用 poster，点击可进入视频项，不在材质层解码。
- 分拆独立 E2E 场景，不将上传、书页、全屏、备注和重启挤入同一个默认时限；不增加全局重试或放宽安全策略掩盖问题。
